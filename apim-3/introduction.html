Who opens API Management

The people who land on the Services catalog, what each of them brings with them, and why the same page fails them in different ways. Read this first — the comparison pages assume it.

Work in progress — review under way, findings still being added

Why this page exists

Every finding in this review comes back to the same thing: the Services catalog is the front door to API Management, and it's built for someone who already knows the product. Setting out the arrivals here keeps each comparison page focused on one problem and one fix, instead of re-explaining the audience every time.

The two use cases

Case 1 — A Classic API Management customer subscribes to APIM 3.0, or starts a trial

Arrives fluent in the old product. Has existing assets.

They know Proxies, API versions, the Developer Portal, and subscriptions. This page says Service, and nothing maps the old vocabulary to the new — so they can't tell whether the page is empty or simply unfamiliar.

Their real first task is migration, but the left nav puts Migration Tool below Manage, under a section heading that sits over a single link and never says what migrates to what. The product opens on a page for browsing assets they haven't moved yet.

They also see two entries named API Manager: the product itself, and the Classic one they recognize. The familiar click leads out of the product they're evaluating. Nothing on screen says whether Classic is deprecated, whether both run side by side, or whether migrating affects live traffic.

Case 2 — A new customer subscribes to APIM 3.0, or starts a trial

No history with the old product. No assets yet.

They don't see the Classic section in the nav at all, so that ambiguity never reaches them. What reaches them instead is the emptiest possible version of this page: no Services, and therefore no rows — because the catalog lists only Project Spaces and Projects that contain Services.

So their first impression of API Management is a page headed Catalog Stats, five zeroes, three filters, and nothing else. Nothing defines a Service, and nothing tells them what to do first.

The variant inside both cases

Whichever situation they come from, somebody on the team goes first — creating a Service, or migrating a Classic Proxy or API version. Everyone else arrives afterward, into what that person built. The two roles need opposite things from the same page.

The first person on the team

Faces a browsing interface with nothing to browse. The only useful action is Add service, parked at the top right of a card below the stats, which never says which Project the new Service lands in.

They also choose the Project Space and Project structure everyone after them inherits — decided blind, at the moment they know least about the product.

Everyone who follows

Has the opposite problem: find my Service inside a structure somebody else chose. This is where the missing search, sort, and counts hurt, and where environment-wide statistics say nothing useful — “48 unpublished” is not a fact about their work.

Permissions help them more than they expect: the list shows only what they can access. But nothing says so, which leaves its own question — is my team's Service missing, or can I simply not see it?

What the product actually does

Four behaviors shape every proposed fix. They're easy to get wrong from a screenshot.

  • The catalog lists only Project Spaces and Projects that contain Services. Empty ones never appear, so every visible row holds something — and a customer with no Services sees an empty page rather than a tree of empty folders.
  • Customers who never had Classic don't see the Classic API Management nav section. The duplicate “API Manager” problem belongs to Case 1 alone.
  • The list is permission-filtered. Users without Admin privileges see only the Project Spaces and Projects they created or were granted at least view access to, as elsewhere in the SnapLogic UI. No two people necessarily see the same catalog, and an admin's view — the one screenshots and documentation get made from — is the most complete one that exists.
  • The rows are two distinct levels. Project Space, then Project, then Service. The page draws both levels with the same folder glyph and joins them into one path string, flattening the hierarchy into text.

The issues

Grouped by what they break, with the user each one hurts most. Built groups link to their comparison page; the rest are drafted and awaiting review.

The page doesn't introduce itself

Built

Hurts: everyone, worst for Case 2

You click Services Catalog and land on a page headed Catalog Stats — the name of the first widget, not the page. Nothing defines a Service, says what the catalog does, or relates it to the Policy Catalog beside it. See pin 1 →

The statistics count the wrong unit, and define nothing

Built

Hurts: followers and anyone doing governance work

Publishing applies to a Service version, not to a Service, so one Service can sit in several buckets at once. The five counts also mix publication with lifecycle, and nothing explains how Private differs from Restricted — where most people guess wrong. See pin 2 →

The rows don't say what they are or what's inside

Next

Hurts: followers most, and the first person sees nothing at all

A row gives you a name and a folder glyph. It never says whether it's a Project Space or a Project, how many Services it holds, or which of them are yours — so the only way forward is to open each one in turn. Every listed row does contain Services, but the page keeps that rule to itself.

Nothing helps you find a Service

Drafted

Hurts: followers, and every customer past the first dozen Services

No search by name, no sort, no pagination, and no result count. The project filter truncates its own label, no control shows which filters are active or clears them, and all three filters are styled closely enough to a disabled control that people may never try them.

Add service hides half of itself

Drafted

Hurts: the first person on the team

The button adds a Service; a caret beside it reveals a second route, adding one from a specification. Nothing explains the difference or when each applies, the menu holds exactly one item, and neither route says which Project the Service lands in.

The navigation doesn't explain itself

Drafted

Hurts: Case 1

API Manager names two different things. Nothing says what Classic means, whether it's deprecated, or which product owns the truth. MIGRATION is a section heading over one link, and Migration Tool doesn't say what migrates to what.

It won't hold up at customer scale

Drafted

Hurts: followers, growing worse over time

Browsing by folder alone doesn't scale: a test environment already holds 71 versions with no search. The list respects permissions but the statistics may not, so the counts can describe an environment the viewer can't see. The page also never states whether the new catalog or the Classic managers is authoritative.

One state where three are needed

Almost everything above gets sharper once you notice that this page renders identically no matter who opens it. It needs to behave differently in at least three situations:

  • Empty — a new customer, or the first person on a team. There are no rows, and nothing says what to do first. This is the most common first view of the page, and it's the state with the least design in it. It's also ambiguous: because the list is permission-filtered, a user who can see nothing gets the same blank page as a user whose environment holds nothing. Those two situations call for opposite advice — create your first Service, or go ask for access.
  • Somebody else's structure — a follower, who needs to locate their own work inside a hierarchy they didn't choose.
  • Mid-migration — a Case 1 customer with assets in flight, who needs to know what has moved, what hasn't, and which product is serving traffic.
