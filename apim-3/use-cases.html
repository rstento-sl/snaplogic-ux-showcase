Use cases and the first experience

Who arrives at API Management 3.0, what they already know, and what they meet when they get there.

Work in progress

When a customer selects API Management from the waffle menu, the Services catalog opens. The Services catalog page and left navigation pane should be intuitive to both Classic APIM and new APIM 3.0 customers from the first encounter throughout their experience. Where it is impossible to be intuitive, helpful microcopy, in-app user assistance, and learn more links to the doc can help them self-serve to onboard quickly and successfully use APIM 3.0.

Use cases that APIM should support

Case 1 — A Classic APIM customer adopts APIM 3.0, or starts a trial

Fluent in the old product. Proxies, API versions, and subscriptions already in production.

They need to:

  • Map what they already know to the new model — what a service is, and what became of Proxies and API versions.
  • Migrate existing assets, and see what has moved and what hasn't.
  • Run Classic APIM and APIM 3.0 alongside each other until the migration finishes, knowing which one serves live traffic.

Case 2 — A new customer adopts APIM 3.0, or starts a trial

No history with the old product. Nothing built yet.

They need to:

  • Learn what a service is and what the product manages.
  • Create a first service, from scratch or from an API specification.
  • Publish it, and understand what each publication status exposes and to whom.

The variant inside both cases

Somebody on the team goes first. Everyone else arrives afterward, into what that person built — so the two roles need different things from the same screens.

The first person on the team

  • Creates the first service, or migrates the first Classic APIM asset.
  • Chooses the Project Space and Project structure the whole team inherits.
  • Needs to know where a new service lands before creating it.

Everyone who follows

  • Finds their own team's services inside a structure somebody else chose.
  • Sees only the Project Spaces and Projects their permissions allow, so needs to know when the view is partial.
  • Tracks the state of their own work, not the environment's totals.

What goes wrong, and when

The issues group by the moment a customer meets them.

On arrival

The page doesn't introduce itself

The heading names the first widget on the page, not the page, and nothing defines a service or says what the catalog is for. Refer to pin 1 →

Blank page

In two cases, the rest of the page is blank: if nobody has created a service yet, or if services exist but the customer's permissions don't let them view any. The page draws both the same way, so a customer can't tell whether nothing exists or nothing is visible to them.

Ambiguous action button

The caret on Add service hides a second way to add one, and nothing says how the two differ. Refer to pin 4 →

Arriving from Classic APIM

Nothing connects APIM 3.0 to Classic APIM

They arrive fluent in Proxies, API versions, and subscriptions, and no page maps that vocabulary to the new one. Refer to pin 5 →

The left navigation pane works against them

API Manager names two things, Migration Tool doesn't say what migrates to what, nothing states how the two versions relate, and collapsed the pane drops every label. Refer to the left navigation pane issues →

After services exist

Ambiguous folder rows

Each row shows a folder icon and a name, so you must open folders one at a time to find anything. The name is a path, <Project space>/<Project>, but both levels carry the same icon, and the root shared folder shows no prefix at all. Nothing tells you how many services a folder holds, which ones are yours, or that every listed folder holds at least one.

The statistics count the wrong unit, and define nothing

Publishing applies to a service version, not a service, and the five counts define none of their labels. Refer to pin 2 → and pin 6 →

Filters appear inactive

The text and box colors resemble a disabled control, which discourages customers from trying the filters at all. Refer to pin 3 →

It won't hold up at customer scale

Opening folders is the only way through the list, and a test environment already holds 32 services across 71 versions. The page does have a search box — it finds services by name and opens the folders that match — but it renders invisible, so nobody reaches it. That's a one-line defect, not a missing feature: the hidden search box. Even with it back, folders stay the wrong default. The data behind the page already names the project each service belongs to, so the list could open with services at the top level, each showing its path — one list to scan, sort, and search, instead of a folder tree to guess at. The list respects permissions; nobody has confirmed whether the statistics do, and if they don't, the counts describe an environment the viewer can't see.
