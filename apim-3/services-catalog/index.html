Services catalog

What's wrong with the page that opens when you go to API Management, grouped by what it breaks and who it breaks it for.

API Manager > Manage > Services Catalog

Work in progress — 2 of 12 issue groups built

The Services catalog is the front door to API Management — it's what opens when you go there — and it's built for someone who already knows the product. Everything below follows from that. For who arrives here and what each of them brings, see the two use cases on the APIM 3.0 index.

The proposal

Current UI and proposed changes Side-by-side comparison with numbered pins. Two issue groups built so far: the page header, and the statistics row. Open →

What the product actually does

Four behaviors shape every proposed fix. Each is easy to get wrong from a screenshot alone, and each rules out fixes that would otherwise look sensible.

  • The catalog lists only Project Spaces and Projects that contain Services. Empty ones never appear, so every visible row holds something — and a customer with no Services sees an empty page rather than a tree of empty folders.
  • The list is permission-filtered. Users without Admin privileges see only the Project Spaces and Projects they created or were granted at least view access to, as elsewhere in the SnapLogic UI. No two people necessarily see the same catalog, and an admin's view — the one screenshots and documentation get made from — is the most complete one that exists.
  • The rows are two distinct levels. Project Space, then Project, then Service. The page draws both levels with the same folder glyph and joins them into one path string, flattening the hierarchy into text.
  • Customers who never had Classic don't see the Classic API Management nav section. The duplicate “API Manager” problem belongs to Case 1 alone.

The issues

Grouped by what they break, with the arrival each one hurts most. Built groups are on the comparison page as numbered pins; the rest are drafted and waiting on review.

The page doesn't introduce itself

Built

Hurts: everyone, worst for Case 2

You click Services Catalog and land on a page headed Catalog Stats — the name of the first widget, not the page. Nothing defines a Service, says what the catalog does, or relates it to the Policy Catalog beside it. See pin 1 →

The statistics count the wrong unit, and define nothing

Built

Hurts: followers and anyone doing governance work

Publishing applies to a Service version, not to a Service, so one Service can sit in several buckets at once. The five counts also mix publication with lifecycle, and nothing explains how Private differs from Restricted — where most people guess wrong, because Private is the status that isn't in the Developer Portal. See pin 2 →

The rows don't say what they are or what's inside

Next

Hurts: followers most; the first person on the team sees nothing at all

A row gives you a name and a folder glyph. It never says whether it's a Project Space or a Project, how many Services it holds, or which of them are yours — so the only way forward is to open each one in turn. Every listed row does contain Services, but the page keeps that rule to itself.

An empty catalog has two opposite meanings

Drafted

Hurts: new arrivals of every kind

Because the list is permission-filtered, a user who can see nothing gets the same blank page as a user whose environment holds nothing. “There are no Services here” and “there are Services here, none of them visible to you” call for opposite responses — create one, or ask for access — and the page distinguishes them in no way. Nothing says the view is filtered at all.

Nothing helps you find a Service

Drafted

Hurts: followers, and every customer past the first dozen Services

No search by name, no sort, no pagination, and no result count. The project filter truncates its own label, no control shows which filters are active or clears them, and all three filters are styled closely enough to a disabled control that people may never try them.

Add service hides half of itself

Drafted

Hurts: the first person on the team

The button adds a Service; a caret beside it reveals a second route, adding one from a specification. Nothing explains the difference or when each applies, the menu holds exactly one item, and neither route says which Project the Service lands in.

The navigation doesn't explain itself

Drafted

Hurts: Case 1

API Manager names two different things. Nothing says what Classic means, whether it's deprecated, or which product owns the truth. MIGRATION is a section heading over one link, and Migration Tool doesn't say what migrates to what.

It won't hold up at customer scale

Drafted

Hurts: followers, growing worse over time

Browsing by folder alone doesn't scale: a test environment already holds 71 versions with no search. The list respects permissions but the statistics may not, so the counts can describe an environment the viewer can't see. The page also never states whether the new catalog or the Classic managers is authoritative.

One state where three are needed

Almost everything above gets sharper once you notice that this page renders identically no matter who opens it. It needs to behave differently in at least three situations:

  • Empty — a new customer, or the first person on a team. There are no rows, and nothing says what to do first. This is the most common first view of the page, and the state with the least design in it.
  • Somebody else's structure — a follower, who needs to locate their own work inside a hierarchy they didn't choose.
  • Mid-migration — a Case 1 customer with assets in flight, who needs to know what has moved, what hasn't, and which product is serving traffic.
