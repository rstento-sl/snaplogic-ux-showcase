Services catalog

What's wrong with the page that opens when you go to API Management, in the order people meet the problems.

API Manager > Manage > Services Catalog

Work in progress — 2 of 9 issue groups built

What the Services catalog is

The Services catalog is the page that opens when you go to API Management. It lists the Project Spaces and Projects that hold Services; expanding one shows the Services inside it. A Service is one API you manage in APIM 3.0 — its versions, its policies, and who can call it.

This page sets out where the catalog falls short of the use cases APIM should support, in the order people meet the problems: with an empty environment, when arriving from Classic, and once the catalog fills up. The proposed changes are on the comparison page, linked at the end.

Before you have anything

What a new customer, or the first person on a team, opens on day one.

The page is blank, and the blank means two different things

Drafted

The catalog lists only Project Spaces and Projects that contain Services, so somebody with no Services sees no rows at all. The list is also permission-filtered — users without Admin privileges see only what they created or can at least view, as elsewhere in the SnapLogic UI. Those two rules produce the same blank page from opposite situations: there are no Services here, and there are Services here, none of them visible to you. One calls for creating a Service, the other for asking an admin for access, and nothing on screen tells them apart. Nothing says the view is filtered at all.

The page doesn't introduce itself

Built

You click Services Catalog and land on a page headed Catalog Stats — the name of the first widget, not the page. Nothing defines a Service, says what the catalog does, or relates it to the Policy Catalog beside it. For a new customer that is their first impression of the product: a heading naming a widget, five zeroes, three filters, and nothing else. See pin 1 →

Adding the first Service hides half of itself

Drafted

The only useful action on an empty page is Add service, and it sits at the top right of a card below the statistics. The button adds a Service; a caret beside it reveals a second route, adding one from a specification. Nothing explains the difference or when each applies, the menu holds exactly one item, and neither route says which Project the Service lands in — which is also the moment the first person sets the structure everyone after them inherits.

Coming from Classic

What a customer with Proxies and API versions already in production runs into.

Nothing connects APIM 3.0 to the product they already know

Drafted

They arrive fluent in Proxies, API versions, and subscriptions, and the page says Service. No page maps the old vocabulary to the new, so they can't tell whether what they're looking at is empty or simply unfamiliar.

The navigation points them back at the old product

Drafted

API Manager names two things: the product itself, and an item under Classic API Management. The Classic one is the name they recognize, so the familiar click leads out of the product they're evaluating. Their real first task is migration, but Migration Tool sits below Manage, under a section heading over a single link that never says what migrates to what. Nothing says whether Classic is deprecated, whether both run side by side, or whether migrating affects live traffic.

Once the catalog fills up

What everyone who arrives after the first person has to work with.

The rows don't say what they are or what's inside

Next

A row gives you a name and a folder glyph. It never says how many Services it holds or which of them are yours, so the only way forward is to open each one in turn. The glyph hides a second problem: Project Space and Project are distinct levels, and the page draws both the same way and joins them into one path string, flattening the hierarchy into text. Every listed row does contain Services — but the page keeps that rule to itself, so people expand blindly anyway.

The statistics count the wrong unit, and define nothing

Built

Publishing applies to a Service version, not to a Service, so one Service can sit in several buckets at once. The five counts also mix publication with lifecycle, and nothing explains how Private differs from Restricted — where most people guess wrong, because Private is the status that isn't in the Developer Portal. The totals describe the whole environment, which tells a user nothing about their own work. See pin 2 →

Nothing helps you find a Service

Drafted

No search by name, no sort, no pagination, and no result count. The project filter truncates its own label, no control shows which filters are active or clears them, and all three filters are styled closely enough to a disabled control that people may never try them.

It won't hold up at customer scale

Drafted

Browsing by folder alone doesn't scale: a test environment already holds 71 versions with no search. The list respects permissions, but it's unconfirmed whether the statistics do — if they don't, the counts describe an environment the viewer can't see. The page also never states whether the new catalog or the Classic managers is authoritative.
