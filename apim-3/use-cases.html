No support for the most common use cases

Work in progress

When a customer selects API Management from the waffle menu, the Services catalog opens. That page and the left navigation pane should be intuitive to both Classic APIM and new APIM 3.0 customers, from the first encounter onward. Where it can't be intuitive, microcopy, in-app user assistance, and learn more links should let them onboard without help.

What each customer needs, and what the page does instead

Case 1 — Adopting APIM 3.0 from Classic APIM

Fluent in the old product. Proxies, API versions, and subscriptions already in production.

  • Map Proxies and API versions onto the new model. No page maps the old vocabulary to the new. Refer to pin 5 →
  • Migrate existing assets, and see what moved. Migration Tool doesn't say what migrates to what, and it sits between the two versions rather than after them. Refer to pins 2 and 3 →
  • Run both versions until migration finishes, knowing which one serves live traffic. API Manager names two things, and nothing in the nav says how the versions relate. Refer to pins 1 and 4 →

Case 2 — Starting fresh on APIM 3.0

No history with the old product. Nothing built yet.

  • Learn what a service is. The heading names the first widget, not the page, and nothing defines a service or says what the catalog is for. Refer to pin 1 →
  • Create a first service. The caret on Add service hides a second way to add one, and nothing says how the two differ. Refer to pin 4 →
  • Know whether the page is empty or just empty to them. The page is blank when nobody has created a service, and when permissions hide every one. It draws both the same way.

After services exist

Somebody goes first and chooses the structure everyone inherits; everyone after arrives into it.

  • Find your team's services inside somebody else's structure. Every row is a folder icon and a path, <Project space>/<Project>. Both levels carry the same icon, the root shared folder shows no prefix, and nothing says how many services a folder holds or which are yours.
  • Understand what each status exposes, and to whom. Publishing applies to a service version, not a service, and the five counts define none of their labels. Refer to pins 2 and 6 →
  • Narrow the list to your own work. The filters' text and box colors resemble a disabled control, which discourages customers from trying them at all. Refer to pin 3 →
  • Get through a list that keeps growing. Opening folders one at a time is the only way through 32 services across 71 versions. The page has a search box, but it renders invisible: a one-line defect. The data names each service's project, so the list could open flat instead, with a path on every row.
