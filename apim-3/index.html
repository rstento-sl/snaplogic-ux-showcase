APIM 3.0 Usability issues

Confusing UI interactions and microcopy across SnapLogic API Management 3.0, with proposed fixes — for PM and engineering review.

Work in progress

Each linked page shows the real screen on the left and proposed fixes on the right. Click a red pin on the left to see what's confusing; click the matching green pin on the right to see the suggested fix.

Some pages also flag an In-app UA opportunity — a place where in-app user assistance (UA), delivered by a tool like Userpilot or Appcues, could work better than static page text. A short guided walkthrough can explain a multi-step or easily-confused setting more clearly than a dense note or a tooltip, without adding permanent clutter to the page.

Cross-cutting issue — capitalization

APIM 3.0 mixes sentence case and title case across the UI — Services Catalog and Catalog Stats in title case, Add service and Filter by tags in sentence case, sometimes within one screen. JellyRoll, the SnapLogic design system, specifies sentence case, so the title-case labels are the ones out of step. Fix the casing on any label a team touches while making one of these changes, rather than leaving it for a separate pass.

Cross-cutting issue — hidden actions

Buttons across APIM 3.0 hide a second action behind a caret, with nothing to say what it does. Add service creates a service from scratch; its caret adds one from a specification — a different task, and the only clue is the arrow. Name the hidden options and say what each one creates, wherever this pattern appears.

The API Management page under Admin Manager's Application Settings is reviewed separately, with the rest of that product's settings pages — refer to API Management in Admin Manager.

Use cases that APIM should support

Case 1 — A Classic API Management customer adopts APIM 3.0, or starts a trial

Fluent in the old product. Proxies, API versions, and subscriptions already in production.

They need to:

  • Map what they already know to the new model — what a Service is, and what became of Proxies and API versions.
  • Migrate existing assets, and see what has moved and what hasn't.
  • Run Classic and APIM 3.0 alongside each other until the migration finishes, knowing which one serves live traffic.

Case 2 — A new customer adopts APIM 3.0, or starts a trial

No history with the old product. Nothing built yet.

They need to:

  • Learn what a Service is and what the product manages.
  • Create a first Service, from scratch or from an API specification.
  • Publish it, and understand what each publication status exposes and to whom.

The variant inside both cases

Somebody on the team goes first. Everyone else arrives afterward, into what that person built — so the two roles need different things from the same screens.

The first person on the team

  • Creates the first Service, or migrates the first Classic asset.
  • Chooses the Project Space and Project structure the whole team inherits.
  • Needs to know where a new Service lands before creating it.

Everyone who follows

  • Finds their own team's Services inside a structure somebody else chose.
  • Sees only the Project Spaces and Projects their permissions allow, so needs to know when the view is partial.
  • Tracks the state of their own work, not the environment's totals.
